MCP Security Review Framework

MCP-DETECT is a research lab and supervised review framework. It captures Model Context Protocol traffic, applies a bounded set of structural and stateful detections, inventories observed trust boundaries, and prepares evidence for a human security reviewer.

Scope statement

This is not autonomous enforcement, complete MCP protection, or a production drop-in. A human reviewer must interpret findings, confirm context, and choose compensating controls.

Claim, evidence, and boundary

Claim

The framework can make selected MCP behaviors observable and produce reproducible evidence for five implemented abuse techniques.

Evidence

Ten rules, two parent anchors, a 4,727-record benign corpus, five compiler gates, and an 18-class adversarial evasion corpus.

Boundary

The data is self-authored, only 5 of roughly 85 SAF-MCP techniques are implemented, and no semantic detection backend exists.

The problem

MCP expands what an agent can touch, but ordinary reviews miss the tool-call layer.

MCP integrations connect agents to filesystems, ticketing, memory stores, web access, and internal services. A conventional configuration review can identify declared permissions, but it may not show what tools were advertised, what arguments moved through them, whether metadata changed mid-session, or whether an undeclared server appeared in observed traffic.

The project asks a narrower question: what evidence can be extracted from MCP traffic, which abuse techniques can be detected from that evidence, and which classes require controls outside telemetry?

Review model

Tooling supports the reviewer. It does not replace one.

A human-led review uses the framework to capture or receive minimized telemetry, inventory servers and tools, run registered detections, inspect findings, compare observed infrastructure to a declared baseline, and report the confidence and limitations of each result.

  • Tool-call abuse: Review file access, path traversal, secret-shaped arguments, and tool-description poisoning.
  • Trust boundaries: Inventory server commands, writable mounts, network egress, and shadow-server candidates.
  • Evidence integrity: Validate schema, hashes, fixture references, session joins, and the path from rule to report.
  • Drift and rug pulls: Compare advertised metadata across a stateful baseline, then distinguish suspicious drift from legitimate updates manually.
  • Control flow: Use findings as evidence for a reviewer. The framework does not claim to understand every semantic instruction or agent decision.

Architecture

Capture once, analyze through bounded paths.

  1. 01 / ObserveTransparent proxyForwards MCP JSON-RPC bytes and emits one JSONL event per message.
  2. 02 / StructureTelemetry schemaNormalizes sessions, server commands, tools, arguments, and direction.
  3. 03 / DetectRules and baselineWazuh handles structural patterns; Python tracks stateful drift.
  4. 04 / MeasureFramework gatesRuns fixtures, joins alerts, measures coverage, and records gaps.
  5. 05 / ReviewHuman assessmentInterprets evidence, validates context, and recommends controls.

Implemented coverage

Five techniques with named detection logic.

Tool poisoning

Flags hidden instructions embedded in advertised tool descriptions. It does not detect every malicious instruction or semantic manipulation.

Credential exfiltration

Correlates a sensitive-file read with secret-shaped content leaving in a later tool argument. Encoded or transformed secrets can evade plaintext matching.

Sensitive absolute paths

Matches a bounded list of high-risk absolute paths used with recognized content-exposing file tools. Renamed tools, new paths, or indirection can evade.

Path traversal

Detects relative path escape patterns such as `../` in file-tool arguments. It does not replace server-side path confinement.

Rug pull

Tracks hash-visible tool or server metadata drift across a baseline. Legitimate upgrades look like drift, and behavior-only changes are invisible.

Detection discipline

Five gates tied to real historical bugs.

Each `detection.yaml` declares its backends, rules, session join, fixtures, status, and known gaps. The compiler checks schema, rule references, fixture references, session-key correctness, and false positives against the frozen benign corpus. The tests reconstruct earlier failures so a new detection cannot silently reintroduce the same class of mistake.

Measurement boundary

The benign corpus, attack telemetry, and worked examples were generated by the project. These results are reproducible, but they are not evidence of performance against independent adversary traffic.

Trust-boundary inventory

An AI Bill of Materials from observed traffic.

The framework can inventory observed MCP servers, tool names, version hashes, session counts, filesystem access patterns, and network egress. A declared known-good inventory can be compared with observations to surface shadow-server candidates.

Classification is deliberately bounded. An unrecognized custom server is reported as unknown and sent to manual review instead of being assigned a guessed trust boundary.

Known limits

The blind spots are part of the result.

  • Coverage breadth: Five of roughly 85 SAF-MCP techniques are implemented.
  • No semantic backend: Semantic prompt manipulation, intent changes, and meaning-preserving obfuscation are not implemented as a detection backend.
  • Behavior-only compromise: A tool can return manipulated results without changing visible metadata.
  • Encoded content: Base64 or other transformations can bypass plaintext secret matching.
  • Legitimate drift: A real version upgrade can look identical to a malicious rug pull at the hash-drift layer.
  • Self-authored data: Independent or held-out traffic is the highest-value next validation step.
  • Offline analysis: The proxy can capture traffic, but the review workflow is not positioned as production inline enforcement.
