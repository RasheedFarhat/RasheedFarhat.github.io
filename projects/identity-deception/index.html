Deceptive Identity Architecture

A self-hosted lab that connects an Authentik identity perimeter to Canarytokens and a Python enrichment service. The goal is to study how a deliberate identity tripwire can produce evidence with less background noise than a general-purpose network honeypot.

Scope statement

This is a proof of concept, not a production identity control. It has not been load tested, hardened for multi-tenant use, or validated as a replacement for authentication, authorization, endpoint detection, or network monitoring.

Claim, evidence, and boundary

Claim

A deliberately placed identity tripwire can connect SSO activity to a structured webhook and an enriched audit record in a controlled lab.

Evidence

Repository configuration, Authentik customization, a self-hosted Canarytokens stack, Python processing code, and captured lab output.

Boundary

The webhook and IP heuristic are not production hardened. Source attribution, delivery integrity, and failure handling require more work.

The problem

High-signal deception at the identity layer.

Network honeypots can collect broad activity, but that breadth also creates noise and maintenance work. This project explores a narrower design: place a token at an identity boundary where legitimate users should never activate it, then preserve the activation as an event for review.

The project does not claim that every activation proves a specific attacker or attack path. It treats token use as a high-priority signal that still needs context, source validation, and incident handling.

Architecture

From identity boundary to enriched event.

  3. 03 / RouteSecure tunnelExternal callback delivered into the isolated lab network.
  4. 04 / ProcessFlask serviceExtracts event fields and appends structured JSONL.
  5. 05 / EnrichThreat contextQueries geolocation and AbuseIPDB for reviewer context.

Implementation constraints

The environment forced real systems work.

ARM64 dependencies

Missing public images required native Canarytokens compilation on AArch64 rather than relying on an expected registry artifact.

Virtualized storage

VirtioFS and Alpine container ownership behavior caused volume and database permission failures that required host and container configuration changes.

Cryptographic inputs

Seed and base64 constraints in the deception stack had to be aligned with the backend library instead of using placeholder values that failed during initialization.

Proxy-obscured IPs

Tunnels and Docker networking replaced or mixed source information. The lab processor scans the complete payload for globally routable IPv4 values instead of trusting one proxy header.

Telemetry processor

A small service with an explicit evidence path.

The Flask service receives the token webhook, extracts a candidate public IP, enriches it with location and reputation context, and appends a JSON record containing a timestamp, token name, candidate source IP, user agent, and enrichment result.

The API key is read from an environment variable rather than embedded in source. The output is append-only JSONL so another SIEM process can ingest it without scraping terminal presentation.

Security review of the prototype

The current code has important hardening gaps.

  • Untrusted IP ordering: Choosing the first globally routable IPv4 value from the payload can misattribute a source when several addresses are present.
  • Webhook authenticity: The repository does not prove signed webhook verification or a separate authentication control on the receiver.
  • Cleartext geolocation request: The current IP geolocation call uses HTTP. A production revision should use an authenticated HTTPS provider or omit the lookup.
  • Silent failures: Broad exception handling keeps the lab running but can hide enrichment and file-write failures. Structured error reporting and health checks are needed.
  • External dependency trust: AbuseIPDB and tunnel providers add availability, privacy, and rate-limit dependencies.
  • Token disclosure: Screenshots or configuration containing a live token URL must not be republished. The portfolio intentionally excludes that asset.

Next engineering steps

What would move the lab toward a hardened service.

  1. Add signed webhook verification, request-size limits, schema validation, rate limiting, and explicit failure responses.
  2. Replace the payload-wide IP heuristic with a documented trusted-proxy chain and normalized source model.
  3. Move all enrichment to HTTPS, add retries with backoff, and distinguish enrichment failure from a low-risk result.
  4. Add unit and integration tests for proxy chains, malformed webhooks, file failures, API timeouts, and multiple-candidate IPs.
  5. Define retention, redaction, and access controls for captured identifiers.
  6. Run availability and recovery tests before any claim of operational readiness.
